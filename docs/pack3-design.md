# 콘텐츠 팩 3 설계 (연말 시상식 · 무대 디자인 빌더 · 투어 지도 · 라디오국)

사용자가 대규모 콘텐츠 아이디어 25개 중 15·12·22·9번을 골랐다. 원칙은 기존과 같다: 규칙은 `frontend/src/game/`의 순수 TS, 수치는 `balance.ts` 한 곳, 서버는 "유저끼리 만나는" 기능에만 규칙을 둔다. **이 문서의 수치는 모두 제안값이고 실제 플레이로 재지 못했다**(만든 뒤 시뮬레이션 스크립트로 맞춘다).

## 공통 작업

- **GameState 새 필드**(모두 선택값이라 없는 예전 저장은 새로 시작한 것으로 읽는다. `SCHEMA_VERSION`은 그대로): `radio`, `tour`, `venue`(내 무대 초안), `trophies: string[]`(시상식 트로피, 최대 200). `persistence.ts`에 `parseRadio`·`parseTour`·`parseVenue`·`parseTrophies`(알 수 없는 ID는 버리고 큰 값은 한도로 줄인다).
- **영구 보너스**는 `packdata.ts`의 `bonuses`로만 합산한다(`BonusState`에 `tour`·`trophies` 추가). 곱하는 쪽은 ×1이 기본이다.
- **탭**: `TabId`에 `radio`·`tour`·`awards`·`venue`를 더하고 `MoreScreen.tsx`의 `ITEMS`에 줄을 넣는다(알림 점 `alerts.ts`: 라디오 정산 대기 6시간 이상 · 투어 도착/완료 · 시상식 투표 중/결과 발표 · 내 무대 좋아요).
- **글을 쓰는 곳**은 무대 이름뿐이다. `common/text.ts`의 `cleanLine`, `assertNotMuted`, `REPORT_KINDS`에 `venue` 추가(신고·관리자 처리 연동)를 같이 붙인다.
- **문서·테스트**: README(기능·변경 표·테스트 수)와 AGENTS(구조) 갱신, 새 순수 규칙마다 `__tests__`, 서버 순수 규칙은 `backend/src/*/__tests__`.

## 9. 📻 라디오국 「모노사파 FM」 (클라이언트만) — ✔ 구현됨

**한 줄**: 24시간 편성표(기기 시간대 0~23시)를 짜 두면, 시간대마다 다른 청취자가 방송을 듣고 코인·팬이 쌓인다. 일반은 낮, 어둠은 밤에 강하다는 두 자아의 성격이 편성 퍼즐이 된다.

**열림**: 팬 10,000명부터(`BALANCE.radio.unlockFans`).

**칸 종류**(한 시간이 한 칸):

| 칸 | 효과 |
|---|---|
| 🎵 곡 | 내가 발매한 싱글 하나. 수입 = 인세 초 × `coinSecs(60)` × 곡 등급(곡 카드 N 1.0 · R 1.15 · SR 1.4 · SSR 1.8, 리마스터 +15%/레벨) × 청취자 배율 |
| 🗣️ 멘트 | 수입 없음. **다음 2시간** 청취자 ×1.25(연달아 둘은 두 번째가 무효) |
| 📢 광고 | 인세 초 × 160 즉시 수입. **다음 1시간** 청취자 ×0.8 |
| 🎙️ 게스트 | 가진 피처링 래퍼 한 명을 불러 **이웃 곡** +10/20/35/50%(일반/레어/에픽/전설). 같은 래퍼는 하루 한 번 |
| ⬛ 비움 | 수입 없음, 다음 1시간 청취자 ×0.8 |

**청취자**: `sqrt(팬) × 시간대 곡선 × 취향`.
- 시간대 곡선(상대값): 출근 07~09시 · 퇴근 17~19시 1.0, 점심 12~13시 0.9, 밤 22~01시 0.8, 새벽 02~05시 0.3 등(24칸 표는 `balance.ts`).
- 취향: 낮(07~18시) 일반 ×1.3·어둠 ×0.7 / 저녁(19~21시) 둘 다 ×1.0 / 밤(22~05시) 어둠 ×1.4·일반 ×0.8.
- 같은 곡이 직전 3칸 안에 또 나오면 ×0.5(피로). 같은 자아 곡이 이어지면 ×1.05씩(최대 ×1.2), 자아가 바뀌는 곡 앞에 멘트가 없으면 ×0.85(이탈).
- 매 시간 ±10% 변수는 `mix(seed, 시간 번호)`로만 정한다(같은 상태는 같은 결과).

**정산**: 스트리밍처럼 **정산 방식**이다(`claimRadio`). 지난 정산 시각부터 지금까지 **완전히 지난 시간만** 계산하고 남는 분은 다음으로 넘긴다. 쌓이는 시간은 최대 24시간. `advance` 엔진에는 넣지 않는다(편성표가 시각 단위라 별도 순수 함수 `radioHour(state, hourStart)`가 더 단순하다).

**팬 수입**: 곡 한 칸마다 팬 `0.03%` × 곡 등급 × 청취자 배율(광고·멘트 칸은 팬 없음).

**목표 균형(만든 뒤 `npm run sim:radio`로 맞춘다)**: 24칸을 잘 짠 하루 ≈ 인세 약 50분 분량 + 팬 약 1%, 대충(곡 하나 반복) 짠 하루 ≈ 12분 분량. 방치 보상이 인세·스트리밍을 압도하지 않게 한다.

**상태**: `radio = { slots: RadioSlot[24], lastClaimAt, seed, guestDay, guestUsed[] }`, `RadioSlot = { k: 'song'|'talk'|'ad'|'guest'|'off', id?: string }`. 처음에는 전부 비움이고 「자동 편성」 버튼이 가진 곡 중 좋은 순으로 채워 준다.

**화면** `RadioScreen`: 24칸 띠(지금 시각 표시, 낮·밤 색), 칸을 누르면 고르기 창, 칸마다 예상 청취자·수입, 경고(피로·이탈), 정산 버튼과 정산 대기 시간.

**테스트**: 곡선·취향·피로·멘트·광고·게스트 규칙, 정산 시간 경계(자정·정각·상한 24시간), 결정성, 저장 검증, 화면 렌더링.

**서버 확장(v2, 지금은 안 한다)**: 친구 방송표 열람 + 하루 한 번 청취(마을 깃발 `village_flags` 패턴).

**구현 결과(처음 설계에서 달라진 것)**: 규칙은 `game/radio.ts`, 수치는 `BALANCE.radio`, 화면은 `RadioScreen`, 시뮬레이션은 `npm run sim:radio`다.
- 멘트: 시뮬레이션에서 멘트·광고가 한 번도 선택되지 않아(곡 한 칸이 언제나 더 낫다) **멘트 뒤 두 칸 ×1.25 → 세 칸 ×1.3**으로 키우고 멘트·게스트 칸이 **팬 0.015%**를 주게 했다. 곡 한 칸 인세 60초 → **100초**, 광고 160초 → **220초**.
- 게스트: 멘트처럼 뒤 세 칸을 붙잡고 이웃 곡을 올린다. 한 편성표에 한 번씩이라 `guestDay`·`guestUsed` 상태는 없앴다.
- 곡 수입은 **그 곡의 자아 인세**, 광고는 두 자아 중 높은 인세로 센다. 리마스터는 +10%/레벨.
- **편성을 바꾸면 쌓인 시간을 옛 편성표로 먼저 정산**한다(처음 설계에는 없었다. 없으면 오래 비워 둔 뒤 편성표를 짜고 지난 24시간을 거슬러 받는다).
- 결과(곡 10개·변수 제외): 자동 편성 ≈ 인세 46분 분량·팬 0.8%/일, 곡 하나 되풀이 ≈ 21분, 곡 4개 순환 ≈ 27분. 처음 목표(45분·12분)에서 되풀이 쪽이 높게 나왔다. 곡 등급이 좋으면 되풀이도 값이 높아서다.

## 22. 🗺️ 순회공연 「투어 지도」 (클라이언트만) — ✔ 구현됨

**한 줄**: 도시 노드 지도에서 노선을 직접 짜서 출발시키면 실시간으로 이동·공연하고, 도시마다 기념품을 모은다. 어디서 어디로 가느냐가 전략이다.

**열림**: 월클 콘서트(`world`) 클리어.

**지도**: 4개 지역 12개 도시(전부 실제 도시 이름, 공연 규모 1~5단계). 도시끼리 비행 노선(그래프)과 비행 시간이 있고, **실시간 환산은 비행 1시간 = 현실 10분, 공연 한 번 = 20분**이다. 5곳 노선이면 대략 현실 2~4시간이라 방치형 리듬에 맞는다.

| 지역 | 도시 | 성격(자아 궁합) |
|---|---|---|
| 아시아 | 서울(출발지 고정)·도쿄·방콕 | 서울 균형 · 도쿄 어둠 선호 · 방콕 일반 선호 |
| 유럽 | 런던·파리·베를린 | 파리 일반 · 베를린 어둠 선호 |
| 아메리카 | 뉴욕·LA·상파울루 | 뉴욕 균형 · 상파울루 일반 |
| 오세아니아·중동 | 시드니·두바이(허브) | 두바이는 환승 시 다음 비행 −30% |

**노선 짜기**: 서울에서 시작해 연결된 도시를 이어 **최대 N곳**(처음 3, 투어를 3번 마칠 때마다 +1, 최대 8). 한 도시는 한 번만. 칸(도시)마다 그 공연에 세울 자아(일반/어둠)를 고른다 — 두 자아를 번갈아 쓰는 설계.

**결과 계산**(`tourLeg`, 순수·결정적):
- 공연 힘 = 그 자아의 전투력(`towerPower`) × 도시 궁합(0.8~1.3) × 노선 시너지.
- 노선 시너지: 같은 지역을 이어 가면 연속마다 +10%, 비행이 긴 노선을 이어 타면 피로 −5%씩, 네 지역을 모두 지나면 완주 +20%.
- 도시 난이도 = 단계 × 기준값. 힘/난이도 비로 S·A·B·C(S 2.0 · A 1.4 · B 1.0 · C 0.5배), 판정은 씨앗(`seed + 투어 번호 × 16 + 칸`)의 변수 ±10%.
- 보상(칸마다): 코인 = 도시 단계 × 300 인세 초 × 등급 배율, 팬 = 단계 × 0.1% × 등급 배율, S는 다이아 = 단계. **이번 주 핫 도시**(주 번호로 정해지는 도시)에서 하는 공연은 코인 ×2(서버 필요 없음).
- 돌발 사건(칸마다 씨앗으로 확률 15%): 이륙 지연(+30% 시간)·대박(팬 +50%)·분실(코인 −20%)·피처링 보유 시 깜짝 게스트(+20%).

**기념품(영구 보너스)**: 도시에서 처음 A 이상을 받으면 그 도시 기념품 1개. 기념품 1개 = 그 지역 갈래 +0.3%(아시아 라임 · 유럽 인세 · 아메리카 팬 · 오세아니아·중동 전투력), 한 지역을 다 모으면 그 지역 +2%, 12개를 다 모으면 칭호 「월드투어 완주」. 합산은 `packdata.ts`의 `bonuses`.

**상태**: `tour = { seed, count(마친 투어 수), active: { route: CityId[], personas: Persona[], startedAt } | null, paid(이미 정산한 칸 수), souvenirs: Record<CityId, 1>, best: { ... } }`. 도착한 칸은 `settleTour(state, now)`가 시각만으로 계산하고 `claimTour`가 한 번에 반영한다(중간 도착분도 받을 수 있다). 동시에 투어는 하나.

**화면** `TourScreen`: 지도(SVG 노드·선, 비행 시간), 노선 만들기(탭으로 이어 붙이기), 자아 고르기, 예상 결과·합계 시간, 진행 중 화면(비행기 이동, 도착 알림), 기념품 도감.

**테스트**: 노선 검증(연결·중복·최대 칸), 칸 시각 계산, 결과 결정성, 시너지·핫 도시, 정산 한 번만, 기념품·보너스 합산, 저장 검증.

**구현 결과(처음 설계에서 달라진 것)**: 규칙은 `game/tour.ts`, 수치·도시·비행 노선은 `balance.ts`, 화면은 `TourScreen`, 시뮬레이션은 `npm run sim:tour`다.
- 도시: 설계표에는 11곳뿐이었는데 **12곳**(4지역 × 3)으로 맞췄다(이스탄불 추가). 서울은 출발지라 공연하지 않는다. 서울에서 곧장 닿는 곳을 도쿄·방콕·싱가포르·시드니·두바이로 줄여서 뉴욕·유럽은 돌아가야 한다.
- 난이도: 처음에는 무한의 계단 층의 적 전투력에 묶었는데 시뮬레이션에서 **중반부터 모든 도시가 S**가 됐다(전투력은 레벨에 따라 계속 크는데 도시는 고정). 그래서 **레벨에 따른 기본 전투력을 뺀 "전투력 배율"**(장비·클릭·전투력 보너스가 만드는 배수)을 도시 난이도 표(1.8·2.5·3.5·5·7)와 견주게 했다. 장비·클릭이 다 차기 전에는 4~5단계가 B~C이고 끝판에야 뉴욕이 A다.
- 시간: 비행 1시간 = 현실 10분 → **6분**, 공연 20분 → **15분**(한 투어가 2~3시간).
- 보상: 처음 값(코인 300초·팬 0.1%)은 한 투어에 팬이 1% 넘게 늘어서 **120초·0.03%**로 낮췄다. 한 투어 ≈ 인세 20~50분 분량·팬 0.2~0.8%.
- 기념품: 설계의 **칭호 「월드투어 완주」는 만들지 않았다**(칭호는 업적 표에서만 생긴다). 대신 지역을 다 모으면 다이아 20, 열두 도시를 다 모으면 다이아 60을 한 번씩 준다.
- 노선 시너지의 같은 지역 보너스는 최대 +30%, 장거리 피로는 최대 4칸. 돌발 사건은 설계대로 15%이고, 투어를 **중단**할 수 있다(끝난 칸은 먼저 정산).
- `tour.started`(출발한 투어 수)를 더해서 중단하고 다시 시작해도 같은 사건이 나오지 않게 했다.

## 15. 🏆 시상식 「모노사파 어워즈」 (서버) — ✔ 구현됨(집계·화면·투표·보상, 배포 대기)

**왜 서버가 먼저인가**: 차트 점수는 시간 시드와 **지금의** 팬 수(`sqrt(팬)`)로 계산해서, 그때의 팬 수가 저장에 남지 않는 과거 순위는 나중에 정확히 되살릴 수 없고, 서버에는 스케줄러도 없다. 그래서 **날마다 상위권을 스냅샷으로 남겨 두는 일을 가장 먼저 배포**해야 연말에 쓸 자료가 쌓인다.

**집계(`awards/`)**
- **구현됨(수집 단계)**: `AwardsService`의 타이머(5분마다 확인)가 **매 정시** 차트 상위 30곡(일반·어둠 각각)을 `award_points`에 쌓는다. 문서 하나 = (한국 시간 날짜, 속성, 곡)이고 `points`(순위 점수)·`hours`(상위 30위에 오른 시간 수)·`revivals`(역주행 시간 수)를 `$inc`로 누적한다. 정시 하나는 `award_ticks`(정시 번호 유니크)의 표식으로 한 번만 더한다. 두 컬렉션 모두 400일 TTL·`CLEAR_COLLECTIONS`. (처음 설계는 요청이 올 때 하루 한 번 스냅샷하는 **게으른 방식**이었는데, 아무도 차트를 열지 않는 시간이 빠지고 하루 한 시점의 변수에 좌우돼서 **정시마다 타이머로 누적**하는 쪽으로 바꿨다. 서버가 계속 떠 있는 pm2 프로세스라 타이머로 충분하다.)
- 점수: 정시마다 순위 점수 `31 − 순위`(1위 30점 … 30위 1점)를 기간 동안 합친다(하루 최대 720점이라 보이는 점수는 24로 나눠 쓴다). 롱런상은 `hours`, 역주행상은 `revivals`의 합이다. 신인상은 저장의 첫 싱글 발매 시각으로 가린다(집계 자료에는 없다).

**부문**(기간 `period`는 `2026`처럼 연 단위, 월 단위 `2026-12`도 같은 구조로 지원):

| 부문 | 정하는 법 | 보상(💎, 1·2·3위) |
|---|---|---|
| 올해의 노래 — 일반 / 어둠 | 속성별 누적 점수 | 100·50·30 |
| 신인상 | 그 기간에 **첫 싱글**을 낸 계정 중 누적 점수 1위 | 50 |
| 역주행상 | 차트 `revival`(역주행) 일수가 가장 많은 곡 | 30 |
| 롱런상 | 상위 30위에 오른 날이 가장 많은 곡 | 30 |
| 🗳️ 팬 투표상 — 일반 / 어둠 | 누적 점수 상위 10곡 후보에 유저가 투표 | 50·30·20 |

- 한 계정은 한 부문에 곡 하나만 후보. **투표**: 부문마다 한 표(`award_votes` `(기간, 부문, 사람)` 유니크), 내 곡에는 못 한다, **가입 7일 이상·팬 1,000명 이상**만 투표 가능(다중 계정 방지). 투표 참여 보상 부문당 💎2(최대 3부문).
- 차트가 팬 수에 크게 좌우되어 「올해의 노래」는 팬이 많은 계정이 유리하다. 그래서 신인상·역주행상·팬 투표상을 따로 둔다.

**일정(2026 연말)**: 집계는 배포일부터, 투표 12월 24일 0시~12월 31일 24시(한국 시간), **발표 1월 1일 0시**, 보상은 1월 31일까지 받는다. 기간 상태는 `awards/rules.ts`의 순수 함수(`phaseOf(now)`)로 정한다.

**API**: `GET /api/awards`(현재 상태·후보·내 투표·발표 결과), `POST /api/awards/vote`, `POST /api/awards/claim`(수상·투표 보상을 부문마다 한 번만, `award_claims`가 `(기간, 부문, 사람)` 유니크). 수상 보상은 서버가 계산한 값을 클라이언트가 `serverRewards.ts`의 `applyAwardClaim`으로 반영한다(다이아 상한 사용, 트로피는 `state.trophies`에 추가).

**트로피 = 칭호**: `trophy-<기간>-<부문>` ID. 칭호 선택에 트로피를 포함하고 효과는 `balance.ts`의 `TITLE_VIBE`와 같은 방식(부문별 갈래)으로 둔다.

**화면** `AwardsScreen`: 단계별 화면 — 집계 중(내 곡 현재 누적 순위), 투표(후보 목록), 발표(**레드카펫 연출**: 3위 → 2위 → 1위 순서로 한 부문씩 공개, 내가 받으면 축하 연출·보상 받기), 지난 시상식 기록.

**테스트(서버 `__tests__`)**: 순위 점수·기간 판정·부문 계산(신인상·역주행·롱런)·투표 자격·후보 선정은 모두 순수 함수로 만들어 시계를 받는다. DB가 필요한 부분(스냅샷 upsert, 중복 투표·중복 청구 인덱스)은 서버를 띄워 확인한다.

**구현 결과(화면·투표·보상)와 설계에서 바꾼 점**
- 서버 `AwardsBoardService`·`AwardsController`(`GET /api/awards`·`POST /vote`·`POST /claim`), 순수 규칙 `rules.ts`(일정 `scheduleOf`/`phaseOf`·`rankScores`·`candidatesOf`·`resultsOf`·`claimItemsOf`·`voteGate`), 프런트 `AwardsScreen`(+순수 화면 `AwardsView`)·`platform/awards.ts`·트로피 칭호(`balance.ts`·`achievements.ts`)·`serverRewards.applyAwardClaim`. 알림 점은 `GET /api/social/summary`의 `awards`.
- **후보·결과는 `award_editions`에 처음 한 번만 적는다**: 후보는 투표 시작 전날(12/23)까지의 누적으로, 결과는 해 전체 누적과 투표로 계산해 한 번만 적고 이후 바꾸지 않는다(집계 자료·투표가 나중에 달라져도 발표가 흔들리지 않게). 집계 타이머가 5분마다, 화면·투표·청구 요청도 같은 `freeze`로 확정한다.
- **투표 참여 보상은 2부문(최대 💎4)**: 설계에는 "최대 3부문"이라고 적혀 있었지만 투표가 있는 부문은 팬 투표상 일반·어둠 둘뿐이라 맞췄다.
- **신인상은 12월 1일 이후 데뷔**: 설계는 "그 기간(해)에 첫 싱글을 낸 계정"이었는데, 2026-11 정식 출시로 모든 계정의 첫 싱글이 올해라서 구분이 없어진다. 그래서 첫 싱글이 해의 12월 1일 0시(KST) 이후인 계정만 신인으로 본다(`scheduleOf().rookieFrom`).
- **올해의 노래 1위 곡은 롱런상·역주행상에서 제외**: 점수가 높은 곡이 롱런까지 휩쓰는 것을 막는 규칙이다(설계에는 없었다). 한 계정은 한 부문에 곡 하나만 오르는 것은 설계 그대로다.
- **트로피는 1위에게만**(`trophy-<해>-<부문>`, 2·3위는 다이아만), 칭호로 달 수 있고 효과는 올해의 노래 +5%·나머지 +4%(`BALANCE.awards.trophyPerk`, 갈래는 `TROPHY_VIBE`). 저장에는 `trophies`만 더해졌고 영구 보너스는 `titlePerkOf`를 읽는 기존 `bonuses`가 합산한다.
- **투표는 확정 버튼으로 한 번 더 묻고 바꿀 수 없다**(`award_votes` (해, 부문, 사람) 유니크). 보상은 한 번의 `POST /claim`이 받을 수 있는 줄을 전부 내준다(`award_claims` (해, 보상 키, 사람) 유니크). 서버가 받았다고 적은 트로피가 저장에서 빠졌다면 화면이 다시 채운다.
- **레드카펫**: 발표 뒤 부문마다 3위 → 2위 → 1위를 한 자리씩 공개하고 본 만큼은 기기(계정·해별 localStorage)에 기억한다. 「전부 공개」가 있다. 별도 효과음·애니메이션은 아직 없다.
- 확인한 것: 순수 규칙 단위 테스트(경계 시각·동점·계정당 곡 하나·후보·결과·보상·자격), 가짜 모델로 단계별 흐름(후보 고정·투표 거절 사유·중복 투표·결과 고정·청구 한 번·알림 개수). 확인하지 못한 것: **실제 MongoDB**(집계 `$sort`+`$group`·`allowDiskUse`·조건부 upsert·유니크 인덱스·TTL)와 실제 브라우저·모바일 화면.
- **배포가 늦어질수록 집계가 비는 날이 늘어난다**: 집계(`award_points`)는 서버에 배포된 뒤부터 쌓이므로 12월 24일 투표 시작 전에 배포해야 후보를 가릴 수 있다.

**위험**: 서버가 꺼져 있던 시간은 비어 있다(지난 순위를 되살릴 수 없다). 재시작이 길어지면 그만큼 점수가 줄어드니 배포는 짧게 한다. 하루에 한 번 정도로 쌓이는 양은 문서 약 100개(속성당 상위 30곡이 하루 동안 바뀌는 만큼)라 용량은 작다.

## 12. 🏗️ 무대 디자인 빌더 「내 무대」 (서버 + UGC) — ✔ 구현됨(배포 대기)

**한 줄**: 장치를 그리드에 놓아 무대를 만들고, 다른 유저가 내 무대에서 공연한다. 공연장을 클리어할수록 장치가 늘어난다.

**장치 14종**(공연장 첫 클리어로 해금, 시작은 3종):

| 종류 | 장치(해금) |
|---|---|
| 💡 조명 | 스포트라이트(시작) · 미러볼(소형 공연장) · 레이저(단콘) · 와이어 액션(유니버스) |
| 🔊 음향 | 스피커(시작) · 마이크 스탠드(지하 클럽) · 서브우퍼(중대형) |
| 🔥 연출 | 불꽃(중형) · 드라이아이스(중대형) · 폭죽(대형 콘서트) · LED 스크린(월클) |
| 🧱 안전 | 안전바(시작) |
| 🖤 분위기(어둠 전용) | 촛불(폐건물) · 감시 모니터(다크웹) · 관 연출(저세상) |

**그리드·점수**: 8열 × 6행(48칸), 칸마다 장치 0~1개. 점수는 순수 함수(클라이언트 `game/venue.ts`와 서버 `venues/rules.ts`가 같은 표·같은 식 — 서버는 형태·장치 ID·해금 여부는 모르므로 **형태와 점수 계산만** 하고, 클라이언트 테스트가 서버 파일을 읽어 비교한다. 마을 `rules.ts`와 같은 방식).
- 네 갈래 능력치: **화려함**(조명·연출) · **음향** · **안전** · **분위기**. 장치마다 기본값 1~3.
- 인접(상하좌우) 규칙: 조명 옆 연출 ×1.25 · 스피커가 가운데 열에 대칭이면 ×1.2 · 연출 장치 1칸 안에 안전바가 없으면 안전 −2(「위험」 표시) · 어둠 장치는 어둠 무대(테마)에서만 분위기에 반영.
- 필수: 조명 1개 이상 + 음향 1개 이상이 없으면 등급 상한 C. 총점으로 등급 E~S.
- **무대 배율** = `1 + 0.05 × 등급 번호`(E=0 ~ S=5, 최대 ×1.25).

**쓰임**
- **내 무대 공연**: 30분마다 한 번, 코인 = 인세 초 × 300 × 무대 배율.
- **남의 무대 공연**: 하루 3곳까지. 코인 = 인세 초 × 180 × (0.8 + 0.1 × 등급 번호). **주인에게 대관료** 💎1(방문자 한 명당, 주인 하루 최대 5, 우편으로 지급·`ref`로 중복 방지).
- **좋아요** 한 무대에 한 번(토글). 주간 인기 무대 상위 3곳은 지난주 보상(💎 30·20·10, 챌린지의 `POST /claim` 패턴).

**서버 `venues/`**: 컬렉션 `venues`(계정당 하나: 이름·칸 48개·테마·점수·좋아요 수·숨김 표시·수정 시각), `venue_likes`(무대·사람 유니크), `venue_plays`(무대·사람·날짜 유니크, TTL). 라우트는 고정 경로(`me`, `claim-weekly`)를 `:id`보다 먼저 선언한다.

| 라우트 | 하는 일 |
|---|---|
| `GET /api/venues/me` · `PUT /api/venues/me` | 내 무대 읽기·올리기(이름 `cleanLine` 2~16자, `assertNotMuted`, 도배 방지 `rate-limit`) |
| `GET /api/venues?sort=popular\|new\|friends` | 둘러보기(페이지) |
| `POST /api/venues/:id/play` | 하루 한도·`(무대, 사람, 날짜)` 유니크로 한 번만, 응답에 무대 배율 |
| `POST /api/venues/:id/like` | 좋아요 토글 |
| `POST /api/venues/claim-weekly` | 지난주 인기 보상 |

**신고**: `REPORT_KINDS`에 `venue`를 더하고 `resolveTarget`이 이름과 칸 정보를 스냅샷으로 남긴다. 처리하면 무대를 **숨김** 처리한다(주인에게 우편 안내, 기존 규칙).

**클라이언트**: 내 무대 초안은 `state.venue`(칸·이름·테마)에 저장하고 「올리기」를 누를 때 서버로 보낸다(서버가 점수를 다시 계산한다). 반영하는 보상은 서버가 정한 무대 배율을 받아 클라이언트가 계산한다(기존 서버 보상과 같은 신뢰 모델이라 조작된 저장은 막지 못한다).

**화면** `VenueScreen`: 편집(그리드 + 장치 팔레트, 능력치 막대, 위험 경고, 등급), 둘러보기(인기·새 무대·친구), 방문(공연 연출 → 보상), 내 무대 통계(방문·좋아요).

**테스트**: 점수(인접·필수·등급)·형태 검증·해금 규칙·서버 순수 규칙, 클라이언트-서버 표 일치 비교, 화면 렌더링.

**구현 결과와 설계에서 바꾼 점**
- 서버 `backend/src/venues/`(`rules.ts`·`venue.schema.ts`·`venues.service.ts`·`venues.controller.ts`·`dto/`), 프런트 `game/venue.ts`·`balance.ts`(`VENUE_DEVICES`·`BALANCE.venue`)·`screens/VenueScreen.tsx`·`platform/venues.ts`·`scripts/venue-sim.ts`(`npm run sim:venue`). 라우트는 설계표 그대로다(`GET/PUT /me`·`GET ?sort=&page=`·`POST /:id/play`·`POST /:id/like`·`POST /claim-weekly`).
- **장치는 15종이다**: 설계서 본문은 "14종"이라고 적었지만 표에 적힌 장치는 조명 4·음향 3·연출 4·안전 1·분위기 3으로 15종이라 표대로 만들었다.
- **장치마다 한 무대에 놓을 수 있는 최대 개수를 더했다**(스포트라이트 6·미러볼 4·레이저 4·와이어 2·스피커 6·마이크 스탠드 4·서브우퍼 2·불꽃 4·드라이아이스 3·폭죽 3·LED 2·안전바 6·촛불 6·감시 모니터 3·관 연출 1): 설계에는 없었다. 없으면 가장 높은 기본값 장치로 48칸을 채우는 것이 항상 최고 점수라 퍼즐이 되지 않는다. 서버는 개수를 넘은 칸 배열을 거절한다.
- **점수 식의 빈칸을 이렇게 정했다**: 점수 = 화려함 + 음향 + 안전 + 분위기(총점 0 아래로 내려가지 않는다). 「조명 옆」은 상하좌우 4칸, 「연출 장치 1칸 안」의 안전바는 대각선을 포함한 주변 8칸, 「가운데 열에 대칭」은 8열의 가운데 선(4·5열 사이)을 기준으로 한 좌우 대칭이며 **스피커 쌍에만** 각각 ×1.2다(서브우퍼·마이크 스탠드는 대칭 배율이 없다). 조명 둘이 한 연출 옆에 있어도 ×1.25는 한 번만 붙는다. 어둠 장치는 일반 무대에도 놓을 수는 있지만 점수에는 어둠 무대(테마)에서만 반영된다.
- **등급 경계는 시뮬레이션으로 맞췄다**: 처음 제안값(10·24·40·56·72)은 처음 장치 세 가지만으로는 D까지만 닿고 대형 콘서트에서 벌써 S가 나왔다. `npm run sim:venue`(담금질로 찾은 잘 짠 무대) 기준으로 **8·18·36·60·84**로 올려, 처음 장치만으론 C(약 19점) · 단콘~중형 B · 중대형~대형 A · 월클 이후 잘 짠 무대만 S(약 85~98점)가 되게 했다. 아무렇게나 놓은 무대(무작위 칸 절반)는 평균 16~29점이라 D~C다. 분위기 장치는 어둠 무대에서 같은 칸 수로 약 7점 더 얹는다.
- **팬 1,000명부터 쓸 수 있다**(설계에는 없었다): 서버가 `saves.fans`를 읽어 올리기·남의 무대 공연·좋아요를 막는다. 여러 계정을 만들어 서로 공연·좋아요를 눌러 대관료(💎)와 주간 인기 보상을 모으는 것을 어렵게 하는 안전선이다(둘러보기는 누구나 볼 수 있다).
- **내 무대 공연은 클라이언트에서만 센다**: 30분 쿨다운(`venue.ownAt`)과 코인은 저장에서 계산한다(서버가 모르는 보상이라 기존 클라이언트 보상과 같은 신뢰 모델). 장치가 하나도 없는 무대는 공연할 수 없다(빈 무대로 인세 300초를 30분마다 받는 것을 막는다). 보상 배율은 올린 무대가 아니라 **지금 꾸미고 있는 초안**의 등급이다.
- **하루 3곳 한도는 먼저 기록하고 센다**: `venue_plays`에 (무대, 사람, 날짜) 문서를 만든 뒤 그 날 문서 수가 3을 넘으면 방금 문서를 지운다. 동시에 여러 곳을 눌러도 한도를 넘겨 허락하지 않지만, 한도 직전에 동시에 보내면 서로 거절당할 수 있다(다시 누르면 된다). 주인의 하루 대관료 5번은 무대 문서의 `rentDay`/`rentToday`를 조건부로 올려 지킨다(우편이 실패하면 그 횟수는 소모된다).
- **좋아요는 `venue_likes`에 주 번호를 적어 둔다**: 지난주 인기 순위는 그 주에 누른 좋아요 수로 센다(총합 `likes`는 정렬용). 좋아요 문서에는 TTL이 없다 — 지워지면 같은 사람이 다시 눌러 숫자가 부풀기 때문이다. 순위가 같으면 먼저 만든 무대가 앞서고 숨김 처리된 무대는 건너뛴다.
- **신고 처리**: 무대를 `hidden: true`로 하고 **이름도 지운다**. 주인이 새 이름으로 다시 올리면 숨김이 풀리고 또 어기면 또 신고할 수 있다(프로필 신고와 같은 방식). 이용 제한 중에는 올릴 수 없고 제한 안내 우편에 「무대 올리기」가 들어갔다. `MAIL_KINDS`에 `venue`(대관료) 종류를 더했다.
- **알림 점은 「받을 수 있는 주간 인기 보상」**이 있을 때 켜진다(`social/summary.venues`). 설계의 「내 무대 좋아요」(새 좋아요가 왔을 때)는 본 적 있는 좋아요를 기억할 곳이 없어서 만들지 않았고, 내 무대 탭에서 좋아요·공연 수를 볼 수 있다.
- **공연 연출**은 칸의 장치가 순서대로 반짝이는 1.8초 연출 뒤 결과(등급·코인·대관료 안내)를 보여 준다(효과음은 앨범 발매음 재사용, 동작 줄이기 설정이면 연출 없이 결과만).
- 확인한 것: 서버 순수 규칙 26개(표·형태 검증·점수·인접·필수·등급·주간 순위), 프런트 규칙·명령·저장 34개, 화면 렌더링 25개, **서버와 프런트 구현이 같은 점수를 내는지 무작위 배치 400개 비교**(상수·표가 한 곳만 바뀌면 실패하는 것도 확인), 가짜 모델로 서버 흐름(올리기 검증·다시 올리기·둘러보기 정렬·쪽·친구·하루 방문 한도와 동시 요청·대관료 상한과 동시 요청·좋아요 토글·주간 보상 순위·중복 청구·알림 개수)과 신고 접수·처리 흐름, 새 모듈이 Nest 의존성 그래프에서 풀리는지.
- **확인하지 못한 것**: 실제 MongoDB(upsert·`$group` 집계·유니크 인덱스·TTL), 실제 브라우저·모바일에서의 모습(8×6 칸을 손가락으로 누르는 크기, 장치 상자 배치), 효과음·애니메이션의 느낌. 점수 표와 보상 수치는 제안값이다.
